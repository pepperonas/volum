# Architecture

Status: **implementation blueprint**, derived from `docs/decision.md`. Where the two
disagree, `docs/decision.md` holds the reasoning and wins.

## 1. Overview

## 2. Process model

Three processes, deliberately.

**Desktop shell (Rust/Tauri).** Owns the window and the lifecycle. Spawns the engine as a
sidecar, passes it a freshly generated session token through the environment, reads the
chosen port from the child's stdout, and terminates it on exit. It holds no pipeline logic.

**Engine (Python).** A long-lived HTTP server on loopback. Holds the job queue and the
model registry. It does *not* run inference in-process.

**Provider worker (Python, per job).** Runs one job in its own interpreter, in the
provider's own virtual environment, and exits. Rationale in `docs/decision.md` §4c: GPU
faults are survivable, cancellation is real, and unified memory is genuinely released.

### Why HTTP over loopback rather than stdio IPC or a Unix socket

Jobs run for minutes and must stream real stage transitions (spec §18 forbids invented
percentages), which makes SSE the natural transport. HTTP also gives one interface that
serves the GUI today and tooling later. `AF_UNIX` support is uneven enough across Windows
tooling to be a liability in a cross-platform product.

Security (spec §50): bind `127.0.0.1` only, port 0 (ephemeral), a per-session bearer token
generated by the shell and never written to disk, and a hard refusal to start if the token
is absent. There is no unauthenticated local endpoint and no fixed port to squat.

## 3. Engine API

Implemented in `engine/src/volum_engine/`; started as `volum-engine`.

### Start-up contract

1. The shell generates a session token (64 hex characters) and passes it in
   `VOLUM_ENGINE_TOKEN`. The engine refuses to start without one, or with one shorter than
   32 characters. There is no unauthenticated mode.
2. The engine binds `127.0.0.1` on port 0 and prints **one JSON line to stdout**:
   `{"event": "listening", "host": "127.0.0.1", "port": 54321, "pid": 4242, "version": "…"}`.
   Everything else goes to stderr, so stdout stays parseable. Fields are only ever added.
3. The shell polls `GET /health` with the token until it answers 200.
4. With `--exit-with-parent` the engine stops when its stdin closes — a shell that crashes
   cannot leave an engine behind holding the GPU. Otherwise SIGTERM.

Every request carries `Authorization: Bearer <token>`, `/health` included, compared in
constant time; anything else is `401` with `WWW-Authenticate: Bearer`. CORS is allowed
only for the desktop webview's origins (`tauri://localhost`, `http(s)://tauri.localhost`,
the Vite dev server on 1420; override with `VOLUM_ENGINE_ALLOWED_ORIGINS`). A browser
tab that guesses the port gets a CORS refusal and, if it gets past that, a 401. The
interactive OpenAPI pages are disabled: they would be the only unauthenticated thing served.

### Endpoints

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | liveness + version; used by the shell during start-up |
| `GET` | `/api/system/doctor?deep=` | full hardware + runtime + per-model verdict |
| `GET` / `PATCH` | `/api/settings` | data directory, Hugging Face token (returned only as `…_set: true`), marginal-model opt-in |
| `GET` | `/api/models` | catalogue with install state, disk usage, verdict for *this* machine, implementation flag |
| `GET` | `/api/models/{id}` | one entry, including the current install task if any |
| `POST` | `/api/models/{id}/install` | `202` — explicit, user-triggered download, runs in the background |
| `GET` | `/api/models/{id}/install/events` | **SSE** install progress (`step`, `message`, terminal `done`/`failed`) |
| `DELETE` | `/api/models/{id}` | remove weights and the provider environment; `409` while installing or in use |
| `GET` | `/api/jobs?limit=` | job records, newest first |
| `POST` | `/api/jobs` | `202` — validate inputs, stage them, queue the job; body mirrors the CLI flags (`model_id`, `images`, `seed`, `formats`, `for_print`, `target_size_mm`, `single_part`, `device`); returns the record plus warnings |
| `GET` | `/api/jobs/{id}` | job record |
| `GET` | `/api/jobs/{id}/events` | **SSE** — full record per event, closes after the terminal state |
| `POST` | `/api/jobs/{id}/cancel` | marks the job cancelled and terminates its worker (SIGTERM, then SIGKILL after 5 s) |
| `DELETE` | `/api/jobs/{id}` | delete a finished job and its directory; `409` while active |
| `GET` | `/api/jobs/{id}/artifacts/{name}` | `mesh`, `export_stl`, `export_3mf`, `quality_report`, `repair_report`, `asset` — served only from inside the job directory, with `model/gltf-binary`, `model/stl`, `model/3mf` media types |

Projects (spec §28) are not yet exposed; a job directory already holds everything a
project needs (`job.json`, staged inputs with hashes, artifacts, quality report, `asset.json`).

### Conventions

Every response is JSON except artifact downloads and the SSE streams. Errors — service
errors, validation errors and unexpected ones alike — have one shape (spec §55):

```json
{"error": {"message": "triposr is not installed.", "technical": null,
           "suggestions": ["Install it first: volum models install triposr"]}}
```

`400` invalid input · `404` unknown · `409` conflict (not installed, already running,
still active) · `422` malformed body · `503` no implementation · `500` unexpected (traceback
in the engine log, only the exception's name in the response).

SSE frames are `data: <json>\n\n` carrying the **whole record**, snapshotted on the
producer's thread at notification time — a late joiner or a dropped frame never loses
state, and a fast pipeline cannot collapse two stages into one frame. A `: keep-alive`
comment is sent after 15 s of silence. The browser `EventSource` API cannot set headers, so
the frontend reads streams with `fetch` and a `ReadableStream` rather than `EventSource`.

Jobs run **one at a time** on a worker thread (one GPU, one job); further submissions wait
as `queued`, visibly. The engine, not the CLI, fails jobs left non-terminal by a crash at
start-up — a CLI command beside a live engine must not declare the engine's jobs dead.

## 4. Provider interface

```python
class ImageTo3DProvider(ABC):
    id: str
    capabilities: frozenset[Capability]      # SINGLE_IMAGE, MULTI_IMAGE, TEXTURE,
                                             # PBR, UV, HIGH_RESOLUTION, FAST_INFERENCE
    requirements: Requirements               # platforms, runtimes, min memory,
                                             # estimated peak, disk, licence metadata

    def validate_environment(self) -> EnvironmentReport: ...
    def estimate_resources(self, params) -> ResourceEstimate: ...
    def generate(self, request, on_progress) -> GenerationResult: ...
    def cleanup(self) -> None: ...
    def metadata(self) -> ProviderMetadata: ...
```

Capabilities and requirements are **declared data**, not branches in the pipeline. The
doctor and the Model Manager compute availability by comparing declarations against
detected hardware. A provider that cannot run here is reported with the numbers — *needs
~24 GB, this machine has 16 GB* — and can be force-enabled explicitly by the user. It is
never silently downgraded to CPU (spec §7).

`MULTI_IMAGE` is `false` on every V1 provider. Multi-image input in V1 means analysing a
set and selecting the best frame, labelled as exactly that (`docs/decision.md` §10).

## 5. Runtime abstraction

`Runtime` describes *how* tensors execute: `mps`, `cuda`, `cpu`. It is separate from the
provider, because the same provider may have several backends — on macOS the TRELLIS.2
provider is expected to move between the MPS port, an MLX backend and, later, a
GGML/Metal backend without the pipeline noticing (`docs/adr/0002`).

`HardwareDetector` reports OS, architecture, CPU, RAM, GPU, unified memory or VRAM where
reliably obtainable, Metal, MPS, CUDA and its version, PyTorch, MLX and free disk. It never
guesses: a value that cannot be determined reliably is reported as unknown rather than
estimated.

## 6. Job system

States: `QUEUED → PREPROCESSING → RECONSTRUCTING → TEXTURING → OPTIMIZING → VALIDATING →
COMPLETED`, with `FAILED` and `CANCELLED` reachable from any active state.

Progress is **stage-based**. Where a provider emits a genuine fraction it is passed
through; where it does not, the UI shows the stage and an indeterminate indicator. No
percentage is ever synthesised.

Each job records id, status, stage, progress, model, model version, runtime, timestamps,
input files, parameters, artifacts, error and logs — persisted so a job survives a restart.

## 7. Pipeline

```
analyze → preprocess → reconstruct → geometry → texture → optimize → validate → export
```

Every stage is a pure-ish function over a job context with explicit inputs and outputs, so
each is testable in isolation (spec §19). Original input files are never modified;
preprocessing writes derivatives (spec §16).

Background removal uses **BiRefNet (MIT)**, not RMBG-2.0 (CC BY-NC), even where an upstream
port defaults to the latter (`docs/licenses.md`).

Validation is mandatory and can fail a job. A mesh that is empty, non-finite or
degenerate is a failure, not an export — upstream has a documented failure mode where the
decoder silently produces an empty mesh, and VOLUM must not turn that into an asset.

## 8. Storage

Platform defaults, overridable, and **relocatable to external storage** (spec §27, and a
functional requirement given the disk budget):

```
<data dir>/
  models/     weights and per-provider virtual environments
  projects/   project.json, source images, artifacts, quality reports
  jobs/       job records and logs
  cache/      input+config hash → artifact
  logs/
  exports/
```

The cache key is a hash of source image hashes, model id, model version, runtime,
parameters and preprocessing configuration. Free space is checked before every install and
every job.

## 9. Viewer

Three.js / React Three Fiber: orbit / pan / zoom / reset, auto-rotate, grid, environment
lighting, wireframe / solid / material / texture preview, background toggle, and asset
statistics. A loaded model is not re-parsed on view changes.

## 10. Packaging

Thin installer, fat data directory. The bundle carries the shell, frontend, `volum_core`,
the CLI and a relocatable interpreter; heavy ML dependencies and all weights install on
first use through the Model Manager. App updates and model updates are independent
(spec §40). macOS builds are arm64-native; no universal binary, because an x86-64 slice
could not run the primary provider.

## 11. Versioning

One version, one source of truth, propagated by script to `pyproject.toml`,
`package.json`, `tauri.conf.json`, the CLI and git tags, and checked in CI.
